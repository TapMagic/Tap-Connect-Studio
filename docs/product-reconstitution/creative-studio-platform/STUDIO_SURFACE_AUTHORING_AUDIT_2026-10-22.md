## New findings beyond the five reported selection defects

| Finding | Evidence and implication | Proposed class / remedy |
| --- | --- | --- |
| Surface is a presentation contract with several persisted mirrors, not one uniform editor path | `platform/surface-capability.ts` reads structured `surfaceTreatment` ahead of scalar aliases. `visual-plane.ts:readContainerVisualPlane` prefers `props.visualPlane`. The Container Material branch in `creative-composition-canvas.tsx:NodeVisual` wins while a non-sourceMaster `materialPreset` remains active. | B: make existing adapters resolve the active treatment explicitly, synchronize relevant mirrors and preserve inactive settings deliberately. No new Material engine. |
| Switching treatment may leave a Material active | `applyStudioSurfaceTreatment` spreads existing props and writes treatment/fill/plane, without clearing `materialPreset` or `gradientFill`. The renderer takes its Material branch first. | A: source-demonstrated precedence hazard; reproduce on clone with Material → Image/Solid/Transparent. A control must either replace the active treatment or explicitly edit the current Material. Do not claim an observed browser failure yet. |
| Editing a scalar Surface parameter can rebuild a plane as solid | `applyStudioSurfaceParameters` creates image/none/solid based on treatment, even when current visual plane contains richer fill information. Saved state can also precede newer aliases. | A/B: test gradient/material → radius/border/opacity changes. Preserve unrelated fill/effect fields; a radius edit must not select a new fill. |
| Container outer and inner geometry are conflated in Inspector | `studio-composition-inspector.tsx:ContainerControls` always renders Responsive size and Flow spacing. `renderContainer` ignores widthPercent, min/max widths and before/after margins when its parent is Layered, using normalized node geometry instead. | A: hide ineffective outer Flow fields in Layered parent; preserve their stored values for reversible mode conversion. Inner Flow gap remains valid in a Flow Container inside a Layered parent. |
| “Alignment” currently serves two relationships | `renderContainer` uses `props.alignment` for outer Flow `alignSelf` and inner non-Layered `alignItems`. | B, conditional: expose the actual combined meaning until separated. Independent outer/inner alignment may need a minimal compatible field extension with fallback from the old value, not a second layout engine. Prove with two current consumers before changing schema. |
| Edit and Preview clipping differ intentionally in code but are not clearly distinguished in UX | Container outer wrapper uses overflow-visible in edit mode; Preview respects `clipContent`. Its inner visual surface uses overflow-hidden and radius, while the outer content wrapper has separate clipping. Root edit also permits overflow. | A: preview clipped content truthfully while selection chrome remains outside clipping. Verify rounded content corners and overhangs. Explicit “Show overflow” diagnostic if needed; never silently change authored bounds. |
| Surface capability clamps can obscure authored values | State reader limits radius to 48, border to 8, opacity to 0.1–1, shadow to 48; sliders match these ranges. Renderer reads some scalar props directly. | A: distinguish supported limits from UI convenience. Values loaded outside UI range need truthful display and explicit normalization, not invisible rewrite on an unrelated edit. Zero opacity must remain distinguishable from transparent treatment where supported. |
| Drag nesting exists in a narrower path than a universal drag contract | Flow pointer code hits explicit drop-parent/index markers and calls canonical reorder/reparent. It does not implement a general dwell-to-nest contract; horizontal/grid paths suppress Flow drop lines. Layered moves use their own existing geometry path. | A for misleading reachability; C for extended nesting UX. Preserve current engines, add shared intent/feedback only when scoped. Keyboard Move to… must name the destination instead of choosing the first Container implicitly. |
| Group is not currently a general Container grouping facility | `renderParentChildren` builds group members filtered to `compositionKind === 'module'`; selection code also checks Container membership. | Do not promise universal Group support. B only if an approved real workflow requires expanding existing Group authority; otherwise C. Alignment and grouping have separate eligibility. |
| Material capability is richer than its discovery surface | `material-engine.ts` contains metallic, enamel, paper, leather, brushed and noise recipes; root and Container inspector each hardcode one Worn Saddle Leather Material card. | C presentation/catalog work, A for any preview/application mismatch. Expose a small validated subset; existence in code does not certify visual quality. |

The Material branch **does** call `resolveMaterialSurfaceFromProps` and `MaterialSurfaceLayers`, as does the root Material path. There is no finding that Container Materials universally bypass the shared renderer. The risk is transition and adapter consistency across Material, Visual Plane and treatment state. Keep the existing distinction between composition structure and visual rendering.

## Anchor contract: source example, not a new interaction pass

The legacy `composition.ts:resolveNodeBox` subtracts fractions of width/height according to anchor. For a normalized node x=.5, y=.5, w=.2, h=.1 in a 400×600 parent, top-left resolves to (200,300)px and center resolves to (160,270)px. This is a reference-point interpretation. Current parent-authority Layered rendering instead places left/top directly from x/y; changing a legacy anchor does not thereby define a resize pivot or rotation origin. Retained UI must name its actual applicable contract. The S1 corrective candidate must prove before/after interaction and reload; these arithmetic examples alone do not pass Anchor acceptance.

Material application should change appearance only: never parentage, geometry, text, actions, access or identity. Proposed preset scope names which appearance properties it replaces; applying a surface preset must not apply recipe `textColor` to unrelated descendants. Keep Material recipe identity/version and local editable values consistent with the existing resource contract.

## Candidate Container presets

These are proposed editable configurations, not new rendering technology or certified catalog entries. Evaluate on real native content, light and dark surroundings, at 390px. Ship only families meeting preview/application/reload parity.

| Family | Proposed native composition | Initial disposition |
| --- | --- | --- |
| Clean minimal | Solid fill, subtle 1px rim, 16px corners, restrained padding, no unnecessary effect | First reference candidate; existing capabilities adequate subject to parity. |
| Glass | Translucent fill, existing backdrop blur, subtle rim; readable fallback against a flat background | Candidate, require browser/render and contrast inspection; do not fake translucency with a flat gray swatch. |
| Metallic | Existing gunmetal/brushed recipe, restrained highlight, subtle depth | Candidate after adapter transition proof; reject noisy texture or banding. |
| Soft dimensional | Low-contrast gradient, soft outer shadow and small inner highlight | Candidate after shadow preservation proof. |
| Editorial | Warm/light solid, clean border, generous spacing, restrained type pairing | Layout/type defaults composed separately from Surface recipe; no hidden child restyling. |

A surface preset does not change Flow/Layered. A separate explicitly named Container starter can include layout, initial content and a Surface recipe. The UI must distinguish “Apply surface style” from “Add designed Container.”

## Effort assessment and measurement limits

Counting rule: one selection, click/tap, committed value edit or drag is one action; typing a phrase is one content-entry action. Record scrolls, panel transitions and corrections separately. Do not count rendering waits as actions. Compare identical start/end states, output and input method. Current sequences below are reconstructed from observed screens and source, **not timed successful end-to-end task trials**. Fresh browser tracing was blocked; no numerical productivity gain is claimed.

| Task / defined start | Current known path and count bound | Technical burden / likely wrong turn | Recommended target, not measured |
| --- | --- | --- | --- |
| Reach Text content from no selection, Inspector closed | Select Text → Edit → scroll to Content. At least 2 activations + scroll, 1 Inspector opening. | Generic Module, geometry before words. | Double-click Text (1 edit gesture) or Select → Edit text (2); 0 panel switches for typing. |
| Reach image source from no selection | Select Image → Edit → scroll → Replace. At least 3 activations + scroll; Inspector → browser is an extra task transition. | Tint/position precede source; provider tabs. | Select → Replace (2), shared browser opens with destination named. |
| Set root solid from Surface already selected, inspector closed | Open Inspector → choose Color mode if needed → change color. 2–3 activations/commits; not executed again. | Must know root vs page vs Container; mode-dependent count. | Surface breadcrumb → Style → color; 3 from arbitrary selection, 1 value edit when task open. |
| Refine a Layered Container width | Select → Inspector → distinguish normalized W from Responsive size; at least 3 actions to select a field and commit, additional scrolling possible. | Two width concepts, one ignored by parent mode. | Drag active resize handle, or Select → Position → W commit; one effective width. |
| Nest into a named Container | Existing explicit Flow drop marker path or Inspector parent list; no cross-mode successful count established. | Parent change vs reorder unclear; first-Container keyboard shortcut is ambiguous. | One explicit valid drag/release or Select → Move to → destination (3). |
| Apply a polished two-Container composition | **Unmeasured.** No independent full construction trial in this audit; missing reference image. | Repeated property hunts and potential fill/effect transitions. | 13-step reference journey; count each action and wrong turn on isolated fixture. |

The missing measured baseline is an acceptance prerequisite, not a reason to invent a percentage improvement. Before implementation in an authorized candidate, record current task traces on a clone, then repeat on the changed candidate. Preserve both traces. Proposed targets: primary task within two deliberate activations after selecting an object; exact properties within one contextual opening; no selection-dependent empty destination; no more than one task surface change for Replace; zero unexpected parent/mode changes. These complement, rather than replace, visual and correctness gates.

## Platform compatibility audit boundary

Existing `prisma/schema.prisma` contains Contact and Campaign models, and the editor already has selection, action/resource, proposal, publication and identity boundaries. This audit did not certify complete future Person, membership, collectible or commerce schemas. Their absence from a narrow search is not a mandate to create them.

| Future domain | Constraint on today's editing design | Work deliberately excluded |
| --- | --- | --- |
| Person/customer/fan, relationships, consent, external IDs, segments | Stable semantic references; appearance edits cannot infer consent, duplicate people or move relationships into visual-node ownership. Audience retains ownership. | New graph/schema, segmentation or consent UI. |
| Membership and entitlements | Keep eligibility evaluation external and deterministic; Preview must distinguish simulated audience from actual access when later approved. | Membership engine, billing sync or eligibility cache. |
| Collectibles, editions, numbered units, ownership/activation, QR/NFC, replacement, provenance, transfer/gifting | Duplicate visual design must not duplicate permanent unit identity. Resource provenance survives restyle/reparent; physical credentials remain outside editable style. | Minting, transfer, replacement lifecycle or NFC provisioning. |
| Purchases, subscriptions, gated benefits, events, preorders/pickup, external billing | Actions reference canonical destinations; displayed content never becomes transaction truth. Reusable templates must not copy customer-specific eligibility. | Checkout, inventory, orders or new entitlement records. |
| Campaigns, scheduled promotions, personalization and conditions | Preserve node identity and external bindings through style/layout changes. Contextual appearance can display readiness without taking over Campaign ownership. | Scheduling/rules engine or Campaign editor inside Inspector. |
| Wallet/retained connections, external fan stack, attribution/analytics | Preserve semantic action IDs and provider provenance; editing a frame does not silently replace tracking or relationship targets. | Integrations, tracking redesign or wallet passes. |
| EverEncore, TapStay and other offerings | Same editor, capability adapters and resource authority; product-specific governance expressed through existing declarations. | Forked editors or generic hypothetical plugin frameworks. |
